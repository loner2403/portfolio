### VyaparDrishti (`PROJECTS[0].caseStudy`)
- period: `Paytm Build for India AI Hackathon · Oct 2026`
- role: `Backend and AI evaluation`
- tldr: Turns photographed bills and spoken sales into one explainable stock-and-cash ledger for small shops, using AI only where the input is messy.
- problem: Small shop owners run on paper bills, often handwritten in Hinglish or Devanagari, and on memory for daily sales. They rarely know what to reorder, where cash is stuck or how much short-term funding they need.
- built:
  - A pipeline that reads photographed and handwritten supplier bills (including Hinglish and Devanagari) and spoken sales, and turns them into one stock-and-cash ledger.
  - Recommendations on what to reorder, where cash is trapped and how much short-term funding is needed.
  - A FastAPI service with 22 endpoints, about 5,600 lines of Python and 262 tests across 24 files.
- decisions:
  - AI only where input is unstructured / Models extract structured events from bills and voice. Everything that involves money, from stock and finance arithmetic to reconciliation, is deterministic Python.
  - Flag doubt instead of guessing / Rule-based confidence flags mark smudged rates and total mismatches so the owner can check them.
  - Choose the model with evidence / An evaluation harness of 8 synthetic bills (smudged, skewed, handwritten and mismatched) and 14 voice clips compared 7 models on parse rate, item mapping, totals and latency.
- results:
  - 100% / bill-total and mismatch-flag accuracy / best of 7 models on the evaluation set
  - 86% / correct stock movements from voice / on 14 voice clips
  - 10 to 15 s / median time per bill / end-to-end processing
  - 262 / tests / across 24 files

### Meeting assistant (new `PROJECTS` entry, second position)
- title `Local meeting assistant`, slug `meeting-assistant`, year 2026, no liveUrl, no sourceCode, empty thumbnail, longThumbnail and images.
- role: `Sole developer`
- techStack: `['Electron', 'TypeScript', 'Python', 'faster-whisper', 'Vitest', 'Playwright']`
- description (two paragraphs joined with a blank line): "A desktop meeting assistant with a transcript panel, an answer panel, notes and a sessions dashboard. Live sessions transcribe the microphone and system audio on the computer itself, in English and Hindi.\n\nNo audio, transcript or request leaves the machine: the app has no network client, and tests check that it cannot reach one."
- caseStudy:
  - period: `Personal project · Oct 2026`
  - role: `Sole developer`
  - tldr: A desktop meeting assistant that transcribes calls on your own computer, in English and Hindi, and never touches the network.
  - problem: Meeting tools usually send your audio to a cloud service, which rules them out for sensitive calls. The goal was an assistant whose transcripts never leave the computer, with privacy promises that are checked by tests instead of stated in a policy.
  - built:
    - An Electron app with a transcript panel, an answer panel, notes and a sessions dashboard with local history.
    - Live transcription of the microphone and system audio in English and Hindi by a local Python process using faster-whisper: large-v3-turbo on the GPU and base on the CPU.
    - Speech is cut into utterances at pauses, and every finished line is written to an on-disk journal before it appears, so a crash loses at most the line in flight and the next launch recovers the session.
    - Simulated sessions that replay hand-written fixtures, clearly labelled SIMULATED, for demos and tests.
  - decisions:
    - No network, enforced / Windows may load only the app's own scheme, every other request is cancelled, a strict Content-Security-Policy blocks outside content, and a test checks that the speech engine owns no sockets.
    - Capture only after consent / Capture code lives in two allow-listed files that a static scan enforces. Permission is denied unless the user has started a live session, and every start and stop is logged; if the log cannot be written, capture is refused.
    - Locked-down windows / Every window runs sandboxed with context isolation and no Node integration, behind a preload that exposes exactly fifteen methods.
    - Test the real app / End-to-end tests drive the packaged app through Playwright, including a probe that confirms network requests are denied.
  - results:
    - 160+ / automated tests / across unit, end-to-end and speech-engine suites
    - 2 / languages / English and Hindi, transcribed on the device
    - 0 / network calls at runtime / checked by a socket test and a network-denial probe

## 3. Readable case layout (shared component)
`src/components/case/CaseBody.tsx` renders, in order:
- `case-tldr`
- results (when present)
- `case-problem`
- `case-built`
- the optional architecture slot
- decisions
- the optional note

`SystemPage` and `ProjectPage` (when `caseStudy` exists) both use it.

Readability rules:
- Section heading: a visible `h2` in the display serif at `text-[clamp(1.75rem,3vw,2.5rem)]`, with a small mono index label above it. It sits in the left column at lg (`lg:col-span-4 lg:sticky lg:top-24 self-start`); the content goes in `lg:col-span-8`.
- Problem: `text-xl md:text-[1.375rem] leading-[1.6] max-w-[34em]`.
- Built: item text `text-lg leading-[1.7]`.
- Decisions: body `text-base leading-[1.7] max-w-[36em]`; title `text-xl`.
- TL;DR: `text-2xl md:text-3xl leading-[1.35] max-w-[34em]` with a 4px left border in the accent.
- Section padding `py-14 md:py-20`.
